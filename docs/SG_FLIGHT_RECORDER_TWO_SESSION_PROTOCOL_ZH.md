# Smart Guard v2.2 — 综合飞行记录仪与严格两次实机机会协议

> 2026-11-02。设计冻结草案；**没有生成可测试 .pack，也没有消耗实机机会**。这是给未来开发与测试执行者的唯一操作入口。旧的 V22_EXECUTION_PLAN_RMB_FIRST_ZH.md 作为原始背景保留，本文件优先。

## 0. 不可谈判的测试预算

- 上限 **2 次**实机：一次 = **启动一次游戏 + 一场自定义战斗 + 在同一战斗内依次操作多个场景 + 提交这场战斗的完整日志和视频**。
- 第 1 次：SG_FLIGHT_RECORDER 的 BASELINE/SHADOW 模式，全程只读；第 2 次：同一记录仪 + 条件式候选补丁 PILOT 模式，完成全功能验收。
- **不准出现第 3 次**，包括“试运行看看日志能否输出”“先做 CCO 测试再回头增加命令监听”“测试不够再让用户补一场”。若第 1 次没能提供足够证据，必须离线分析或标记证据不足，不继续消耗用户游戏机会。
- 如果第一次否定了所有实现候选，**取消第二次**，先做离线/Native 静态研究。未执行的机会不能被当作已验证。
- 一次性开发 **一个记录仪源码版本**，测试前锁定 git commit + SHA256；两次实机使用同一个记录仪不变。第二次只可新增单独的候选行为模块与当前版本 DB 最小差异包，不可重写/改变记录仪。
- 用户没有义务亲自修改脚本、编辑状态 Key、拷贝 API 或处理日志；开发侧必须预制包、操作卡、日志解析器和离线回放工具。

## 1. 开发侧必须一次做完的记录仪模块

| 编号 | 模块 | 一次性采集任务 | 不能误称为已证实的能力 |
| --- | --- | --- | --- |
| M0 | 自检与能力注册表 | 打印 build、包标识、启动/结束、CCO 表达式可用性、命令处理器注册结果、错误统计 | 不支持的 CCO 表达式必须记录 UNAVAILABLE，不伪造值 |
| M1 | 参战单位静态清单 | 玩家所属、unit:type、UI ID、弹药、射程、初始位置、单位类型/分类 | Lua 查询不到的当前 DB 原始字段由离线 RPFM 补齐 |
| M2 | 命令与选择监听 | Move、Move Orientation Width、Move Rotation Angle、Attack Unit、Withdraw、Halt、Fire At Will、Change Skirmish、Special Ability；选中/取消选中事件，能读的 target ID | Move 不提供已验证的发令单位/来源；Attack Unit 的 unit 是目标。不能把选中兵牌当成真实发令单位 |
| M3 | 行动时序 | 位置 x/z、方向 bearing、ordered_position/ordered_bearing、is_moving、is_in_melee、is_routing、player/script control | ordered_position 在 Attack 时经常返回当前位置，不能直接判断玩家意图 |
| M4 | 射击与装填 | 当前目标 ID、目标距离、是否射程内、ammo_left、起始弹药、CCO IsFiringMissiles/ReloadPercentMax/PrimaryAmmoPercent | ammo 不变或 IsFiringMissiles=false 单独都不等于受阻 |
| M5 | 遮挡状态探针 | CcoBattleUnit.StatusList / StatusMostImportant；尝试读列表长度、每项 Key/Tooltip/IconPath 的多个**预设**候选路径 | 文档存在不保证战斗 Lua 可访问；不存在稳定 Key 时记 UNKNOWN |
| M6 | 备用目标快照 | 以低频扫描最多若干有效敌军：射程、距离、方位夹角、是否有效目标；取分数前 5 名 | 射程/朝向只能筛选候选，不能证明每支弓枪有可射线 |
| M7 | 影子转火引擎 | 在不下命令的情况下产生 WOULD_RETARGET/REJECT 与原因：未受阻、保护人工命令、冷却、没有更好目标、候选已失败 | 不执行攻势，不能声称预测必然命中 |
| M8 | 数据完整性与性能 | 每模块心跳、成功/失败次数、采样次数、丢弃日志条数、所追踪单位列表、日志序号、终止原因 | 游戏计时不是 CPU 计时；没有 CPU 探针时只报告粗略负载/采样预算 |

架构：M0 单独初始化，各模块互相隔离；任何 CCO 查询、context 操作、单位对象异常只能关闭**该字段/该模块**，不能使主记录仪崩溃或重启。M2/M3/M4 永远先于 M5/M6 工作；M7 只读并受 M0 能力表约束。

### 预埋的 CCO 降级流程，不能测试后再回炉

1. 初始化先尝试 CCO 基础标量的实际访问签名，成功则登记 TYPE；失败则逐项记录错误码/类型，只对本测试的预设表达式变体做有限次数探测。
2. 对 StatusMostImportant / StatusList，只尝试预置的 Size/元素路径变体。不要假定 StatusList.At(i).Key 必定可用，更不要编造 'obstructed' 的硬编码 Key。
3. 如果状态列表全部不可读，仍采集单位命令、弹药、移动、装填与 UI 视频，打出 CCO_UNAVAILABLE，继续整个测试。禁止静默 false。
4. 对每个失败字段熔断，仅首次和最终统计写日志，严禁 100ms 重复报错。

### 观测频率与日志保障

- 只允许 4 个主要单位进入 100ms 高频轨迹采样（两支同类弓手、一支直射枪兵、一支火炮）；其它单位只建立轻量静态清单。
- CCO 状态与装填可 200–500ms 采样，目标候选快照 500–1000ms；命令、目标变化、模式变化及模块错误立即写事件。
- 普通采样写“变化量/关键变化 + 定期快照”，每 5 秒写 HEARTBEAT；重要命令事件立即输出，其他记录设置有界缓存与写出节流，避免海量日志。
- 首选官方 out() 写入游戏 script_log，并以独有前缀 [SGFR] 输出单行结构化 JSON。不要假定游戏 Lua 拥有独立磁盘文件写入能力。离线工具从 script_log 提取 sgfr.jsonl。
- 逐条日志含 seq、battle_time_ms、recorder_build、mode、kind、uid、target_uid、field_value、field_valid、error、estimated_source、confidence。未观测到与 false 不能混淆。
- 不提供 UnitController 实例、不调用 halt/attack_unit/goto/release_control、不加减速技能；第一轮必须完全只读。
- 在日志开头写 [SGFR] BOOT_OK、能力表；结尾写 FINAL_SUMMARY（累计事件数、样本数、丢弃数、各模块状态）。如未到结尾，离线解析器报告 TRUNCATED，不要求重新实机。
- 场景标签用一个固定单位的选择事件作辅助标记，并全程录屏与时间轴对照；不假定存在可靠 RMB 键盘钩子。录像是人工确认“真遮挡、真 RMB、实际是否开火”的证据。

## 2. 第 1 次实机：ONE BATTLE = 集中收集全部诊断

必须禁用 v2.1 Smart Guard（含历史版）及其它下达单位命令的同类 MOD，以避免污染原生基线；不允许中途切 MOD 重启。使用单一预先固定的陆战地图、军队、难度和兵种，建议两支同类弓手 + 一支直射枪兵 + 一支火炮 + 1 支可遮枪线的友军步兵，敌方至少两种目标。固定测试地图和部署截图，供第二次复刻。

| 阶段 | 玩家在**同一场战斗**中要做的事 | 记录仪同时完成的分析任务 |
| --- | --- | --- |
| T1-0 启动与校验 | 进入战斗，暂停部署，依次选中四支记录单位；随后正常开战 | M0 能力测试 / M1 单位清单 / M2 selection / 固定初始坐标 / 日志 BOOT_OK |
| T1-1 正常射击 + 装填 | 选中弓手与直射枪兵，开启 Guard + Fire at Will，让正面射程内敌军暴露并连续射击 | 状态 Key 正常基线、IsFiring、装填曲线、弹药变化、阵型中心、射程/射界、M7 不转火理由 |
| T1-2 友军遮挡 | 将枪兵布置在友军密集队列后方，尝试对正面敌人开火 | 对照黄色受阻 UI、StatusList、弹药/装填、目标变化、引擎是否自行寻路、候选名单 |
| T1-3 地形遮挡 | 使用预设地形/坡地遮挡一支射手；仍处于敌军威胁范围内 | 区分地形遮挡与友军遮挡、能否识别共同稳定状态、移动是否来自 LOS 寻路 |
| T1-4 射程 + 转向 | 分别指向射程外、侧面/背面的敌人，观察原地转向或整队走位 | 确认出射程与真正遮挡的状态区别、bearing/ordered_bearing/position、DB 转向基线 |
| T1-5 自动选敌 + 人工指定 | 让 Fire at Will 自行选一次目标；随后 RMB 明确指定另一个敌人，保留片刻 | 捕获目标切换、人工指令事件、是否能定位下令单位；M7 影子候选评分、人工目标保护 |
| T1-6 玩家指令压力测试 | RMB 地面移动 → RMB 拖拽阵型 → 转向 → Shift 连续 2 段 MOVE | 获取已知玩家命令与单位运动的对照时间线，识别命令事件缺失、目标遗留与选择关联误判 |
| T1-7 特殊命令与收尾 | 火炮手动攻击地面、Guard/Fire-at-Will/Skirmish 切换；最后执行撤退（不可逆，放最后） | 标定火炮攻击地面是否有可识别事件、排除条件、Withdraw 保护、结束摘要/健康检查 |

如果动态战场导致某个实验条件不可复现，只能标记 SCENARIO_NOT_REPRODUCED / UNKNOWN；**不得要求回场补测**。不要在不知道遮挡状态 Key 的前提下要求用户临时改 Lua。

**第 1 次后，开发侧自行离线完成：**
1. 原始 script_log → JSONL → 时间线 → 状态映射与混淆矩阵（正常/装填/遮挡/超射程/人工移动）。
2. 对每条疑似自行寻路，按时间回放：RMB/选择/目标变化 → firing/reload/status → 是否 moving → Δ位置/朝向。
3. 离线影子算法跑同一组日志，统计误判、候选前 5、玩家命令保护覆盖率；无法确认的事件只能报 UNKNOWN。
4. 静态读取 CA 9.x RPFM/DB，核对 fire_arc 与 fire_arc_close 实际列定义、单位转换和共享 battle_entity 引用，先生成最小 DB diff、验证引用。
5. 预制第二次的候选模块与测试包；如果 CCO 遮挡 Key 不稳定，**取消状态驱动自动转火原型**，只能让第二次测试 DB 转向候选；如果 DB 静态不成立亦取消对应模块。

## 3. 第 2 次实机：ONE BATTLE = 集成验收，不再发明新观测任务

仍用同一记录仪源码与日志格式。只替换/新增独立功能模块；观察包不改。使用**同一地图、同一阵容、同一部署**；两支同类型射手分别设为 CONTROL（不接受自动转火）和 PILOT（允许经过验证的受阻转火），其它单位继续观察。DB 变更是固定 pack 级变化，以 T1 原版基线为跨场次对照；Lua 自动转火可以同场两组对照。

| 阶段 | 同一场战斗操作 | 验收内容 |
| --- | --- | --- |
| T2-0 自检 | 进入战斗、选中记录单位 | 校验记录仪哈希与 T1 相同；模式、补丁版本、DB 差异清单、无 v2.1 干扰、所有模块启动健康 |
| T2-1 正常火力 | 正面无遮挡射击 + 一次装填 | 正常攻击与弹药输出不得因补丁消失，记录对照组/处理组差异 |
| T2-2 遮挡与转火 | 复刻友军、地形遮挡；如果 P1 通过，在处理组观察自动转火，对照组保持原样 | 实际是否发射、转换目标次数、是否来回切换、无替代目标时不胡乱下令 |
| T2-3 侧后转向 | 复刻 T1 射界与转向操作 | 如果有 DB 候选，比较转向/中心位移/开火延迟和视觉表现；不能背身异常开火 |
| T2-4 RMB 与 Shift | 处理组启用时做 RMB 地面移动、拖拽/旋转、指定射程外攻击、Shift 2 段 MOVE | **任何一个玩家明确命令被覆盖 = FAIL**；验证即时性，不接受“先关闭技能” |
| T2-5 特殊命令 | 火炮攻击地面、Skirmish、Guard/Fire at Will、最后 Withdraw | 非适用单位不应被接管；保留原版命令结果 |
| T2-6 结束与负载 | 保持数支部队交战并结束本场战斗 | 日志落盘完整、无循环发令、无异常日志洪水、核对最终 Summary |

如遮挡状态未通过 T1 门槛，T2-2 仅作为观测/DB 比较，**禁止临时改成猜测式 Lua 转火**。如没有任何达到离线预检门槛的候选，第二次机会不消耗。

## 5. 离线放行条件（不满足则不要求实机）

- 完成当前游戏版本、接口签名、打包名与 Lua 目录路径核对；不得带着未知函数名让用户实机试错。
- Lua 语法检查，pack 格式/索引/压缩正确，启动代码不会覆盖其他命令处理器；静态依赖检查和版本锁定。
- 使用 Mock battle_unit、Mock CCO、Mock command handler 进行完整离线回放覆盖：字段可读、字段缺失、nil/false、有异常、目标死亡、选中单位变化、脚本命令伪装成玩家命令、重复装填、同帧多事件。
- 验证两轮日志同一 JSONL Schema，解析器对于缺字段、重复、截断、状态故障仍能生成完整/部分报告；实现自检与 FINAL_SUMMARY。
- 单位控制操作静态禁止：首轮源码 grep/AST 不得出现 halt(), attack_unit(), goto(), release_control() 等下发行为；第二轮只允许独立候选模块持有 UnitController，并具显式开关/白名单/冷却/退出条件。
- 检查其他 Smart Guard 实例被禁用；不要依赖同一个 .pack 的自动加载顺序。给用户一份**固定、一页的操作卡**，而不是让他读这些研究文档。

## 6. 一次实机需要用户提交的材料（不追要额外测试）

每次仅一次性提交：（A）该场战斗对应原始 script_log；（B）同场连续录屏（显示状态图标和操作过程）；（C）游戏构建版本与启用 MOD 清单/截图；（D）地图与部署截图（第一轮用于第二轮复刻）。不要求生成多个新日志、修改 Lua 或拿调试器。

## 7. 关键不确定性与诚实报告

- 战斗脚本中 Move 的事件缺乏可信单位/玩家来源；Attack Unit 只有目标 ID；视频只是证据标注，不能把相关性变成引擎可用的精准来源信号。
- CCO 文档记载 StatusList/IsFiringMissiles，但不保证 runtime 可读；无法读就标 UNKNOWN，不无限重试。
- 区分“单位中心没动”和“每个士兵都没动”需要额外层级的引擎接口；当前 Lua unit:position() 只有兵牌中心，细节以视频补充，不能声称微观无移动。
- 日志与录像只能说明对应场景发生的事实，不能凭一次成功证明所有地图/兵种都无问题；第二次后发布实验版需明确适用范围。
- 最大两次**游戏测试**是预算上限，不是保证一定找出可行的无感修复；出现证据缺口时停止，不向用户索要第三次。
